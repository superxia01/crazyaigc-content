# Codex 入门教程：企业如何用 AI 编程做内部工具

企业使用 Codex，不必一开始就做复杂系统。更适合的入口，是把团队每天反复处理的小工具、小页面、小脚本和数据整理流程交给 AI 辅助完成。

## 哪些内部工具适合用 Codex 起步

适合新手和企业团队的场景包括：

- 把 Excel 或 CSV 数据整理成报表。
- 做一个内部查询页面。
- 批量处理图片、文档或文件名。
- 生成活动报名、客户跟进或库存管理小工具。
- 给现有网站新增一个落地页。
- 修复表单、导航、样式和文案问题。
- 写一个自动化脚本，减少重复操作。

这些任务边界清楚、验收标准明确，适合让 Codex 执行。

## 第一步：把需求写成可执行任务

不要只说“帮我做个工具”。更好的写法是：

```text
请做一个内部客户跟进表页面。
字段包括客户名称、联系人、需求、跟进状态、下次跟进时间。
先使用本地 JSON 数据，不接数据库。
页面需要支持新增、编辑、搜索和按状态筛选。
完成后请运行 npm run build。
```

任务越具体，Codex 越容易给出可验证结果。

## 第二步：让 Codex 先读项目

如果你已经有网站或系统，先让 Codex 读取相关文件：

```text
先查看当前项目的技术栈、路由结构、组件风格和数据文件。
不要直接新建一套风格，沿用现有 Tailwind 和组件写法。
```

企业内部工具最怕“能跑但不像原系统”。先读项目可以减少返工。

## 第三步：小范围实现，不要一次做太大

第一版内部工具只需要跑通核心流程：

1. 页面能打开。
2. 数据能展示。
3. 关键操作能完成。
4. 构建能通过。
5. 业务负责人能看懂。

不要第一版就要求权限、数据库、导出、通知、审批和复杂报表全部完成。可以先做可用原型，再逐步增强。

## 第四步：让 Codex 运行验证

每次修改完成后，至少要求：

```text
请运行 npm run build，并检查新增路由能正常访问。
如果有报错，先修复再总结。
```

如果是数据脚本，可以要求 Codex 输出处理前后样例，避免静默错误。

## 第五步：人工检查业务含义

Codex 可以写代码，但企业仍然要人工检查：

- 字段是否符合真实业务。
- 文案是否会误导客户或员工。
- 是否泄露内部系统地址、价格或敏感信息。
- 数据处理结果是否正确。
- 页面入口是否放在合适位置。

AI 编程的原则是：AI 执行，人验收。

## 一个适合企业的练习任务

你可以从这个任务开始练习：

```text
请在现有网站中新增一个内部培训资料清单页面。
页面展示资料标题、适用部门、更新时间、负责人和下载链接。
先使用本地数组模拟数据。
沿用现有 Tailwind 风格。
完成后运行 npm run build。
```

这个任务可以训练 Codex 读取项目、创建路由、写组件、处理数据和运行构建。

## 常见错误

### 需求太大

“做一个 CRM 系统”太大。可以先改成“做一个客户跟进列表页面”。

### 不给现有上下文

没有告诉 Codex 技术栈、页面风格和不能动的文件，容易导致风格混乱。

### 不运行验证

只看代码不够。至少要构建、访问页面或运行脚本。

### 忽略权限和数据风险

内部工具如果涉及客户、财务、合同或员工信息，要先设计权限和脱敏。

## FAQ

### 非技术人员可以用 Codex 做内部工具吗？

可以做简单原型，但涉及生产系统、数据库、权限和客户数据时，需要技术人员审核。

### Codex 适合替代开发团队吗？

不适合。Codex 更适合减少重复开发、修复小问题、生成原型和辅助验证。架构和风险仍然需要人负责。

### 企业从哪个任务开始最合适？

从一个低风险、可验证、能节省时间的小工具开始，例如资料清单、客户跟进表、批量文件处理或简单数据报表。
